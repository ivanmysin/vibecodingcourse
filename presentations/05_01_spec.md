# Спецификация проекта

**Урок 5.1 · Модуль 5. Реализация большого проекта**

15 минут

---

## Что такое спецификация

**Спецификация** — документ, где вы с агентом заранее договариваетесь,
что должно получиться на выходе.

Это **контракт** между вами и агентом:

- что делаем
- чего не делаем
- что можно трогать
- как реагируем на ошибки
- какие инструменты используем

Чтобы не выяснять это постфактум.

---

## Спецификация отвечает на «ЧТО», не «КАК»

- Что на входе и что на выходе каждого шага
- Какие правила без исключений (инварианты)
- Что делать в граничных случаях
- Что НЕ делаем в этой итерации
- Как понять, что готово (критерии приёмки)

Как именно писать код внутри — агент решает сам.

---

## Общая идея: spec → plan → task

```
идея → спецификация → план → задачи → код → проверки
```

- **Спецификация** — что делаем (замысел)
- **План** — как устроено (компоненты, решения)
- **Задачи** — нарезанные атомарные шаги, по одному за сессию

Спецификация живёт в репозитории, версионируется и ревьюится,
как любой другой файл.

---

## Спецификация для научного пайплайна

У науки нет «эндпоинтов» и API — вместо них скрипты и их входы/выходы:

- **Научный вопрос** — что хотим узнать
- **Данные** — откуда, в каком формате
- **Пайплайн** — шаги обработки, каждый сохраняет результат в файл
- **Инварианты** — «данные только из `data/raw/`»
- **Граничные случаи** — пропуски, выбросы, битые файлы
- **Вне scope** — что не делаем в этот раз
- **Критерии приёмки** — проверяемые пункты «да/нет»

---

## Три поля, без которых SPEC — не контракт

```
## Границы
- Читать: data/raw/**, data/codebook.md
- Писать: scripts/**, figures/**, reports/**
- Не трогать: data/raw/**, .env

## Остановка
- 3 одинаковые ошибки → стоп и вопрос.
- Метод не работает → обновить SPEC, не «выполнять любой ценой».

## Доказательства готовности
- results/ranking.csv; figures/*.png; лог make all;
- отчёт с числами из results/.
```

Границы нужны, чтобы субагент знал, что можно трогать. Остановка — чтобы не повторял ошибку бесконечно. Доказательства — чтобы «готово» было проверяемым.

## Каскадные пайплайны

Пайплайн строится **каскадом**:

- каждый этап читает результат предыдущего
- каждый этап сохраняет **все** свои результаты в файлы

Что это даёт:

- воспроизводимость (можно перезапустить с любого этапа)
- проверку промежуточных результатов глазами
- логирование (урок 2.3) становится естественной частью пайплайна

## Совет: обсуди спецификацию с разными LLM

До начала реализациив обсудите спецификацию  **разные моделями**:

- одна модель заметит граничный случай
- другая — неоднозначность в критериях
- третья — лишний шаг или неучтённое ограничение

Это «второе мнение» на этапе планирования —
как в уроке 2.5, но применяется к спецификации, а не к коду.

## Инструменты

- **OpenSpec** — opensource инструмент для SDD: рабочий цикл
  explore → propose → apply → archive
- **GitHub Spec Kit** — набор шаблонов «спецификация → план → задачи»

Для нашего курса достаточно одного файла `SPEC.md` в корне проекта,
который мы заполняем через агента.

---

## Недостатки SDD в науке

Наука — это исследование: не всегда знаешь заранее, что получится.

Возможна ситуация: запланировали, а план оказался **невозможен** —
данные в другом формате, метод не работает на этих данных,
предположение не подтвердилось.

Поэтому спецификация — **живой документ**, а не догма:

> Обнаружил, что план не реализуется → остановитcь и обнови спецификацию, а не «выполняйте любой ценой».

## Итог урока

- Спецификация = контракт с агентом до написания кода
- Общая идея: spec → plan → task
- Для науки: скрипты вместо API, каскадные пайплайны, сохранение в файлы
- В SPEC есть границы (что читать/писать), остановка и доказательства готовности
- Обсудите спецификацию с разными LLM до реализации
- Спецификация — живой документ, особенно в науке
